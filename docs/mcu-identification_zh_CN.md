# 目标芯片识别

[English](mcu-identification.md)

界面上的「目标」一行原来只有一个内核名（`Cortex-M7`），而 H742、H743、H750、H753
回答的内核名完全一样。真正能区分它们的是厂商放在调试单元旁边的**器件 ID 寄存器**。

## 原理

| 项 | 值 |
|---|---|
| 寄存器 | `DBGMCU_IDCODE` |
| 地址（H7 新一代） | `0x5C001000`（APB3 / D3 域） |
| 地址（其余 STM32） | `0xE0042000` |
| 位域 | `[11:0]` = DEV_ID，`[31:16]` = REV_ID |

程序先读表里第一个地址，读不到（H7 以外的芯片在这个地址上会 FAULT，`readMem32()`
自己会清掉粘滞错误）再读下一个。都读不到、或者 DEV_ID 不在表里，就退回只显示内核名
—— 行为与加这张表之前一致。

## 数据文件：`mcu-ids.txt`

**表不在程序里，在 exe 同目录的 `mcu-ids.txt`**（UTF-8）。程序每次识别目标都会重读它，
所以改完不用重启，点一下界面的「刷新」就生效。

```
# 每行一个器件，字段用 | 分隔
#     <寄存器地址> | <值> | <厂商> | <器件名> [ | <掩码> ]
0x5C001000 | 0x450 | STMicroelectronics | STM32H742/743/750/753
0x10000100 | 0x52840 | Nordic Semiconductor | nRF52840 | 0x1FFFF
```

- `#` 开头是注释，空行忽略；
- **掩码可省略，默认 `0xFFF`**（ST 的 12 位 DEV_ID）。Nordic 的料号是 20 位
  （`0x1FFFF`），Artery 的编码铺满整个寄存器（按系列范围给掩码）。比较方式就是
  `(读到的 & 掩码) == (值 & 掩码)`；
- 地址探测顺序**就是文件里的出现顺序**，常用地址放前面能省一次失败的往返；
- 器件名**不能含 `|`**，可以带空格和 `/`；
- **文件没有时只用程序内置的几条**（STM32 常见型号 + nRF52840/832/833/820 + AT32F403A），
  不会自动生成文件，也不会因为没有文件就完全不识别；
- 完整表随发布包一起放在 exe 旁边（源文件在仓库根 `mcu-ids.txt`），
  想加型号直接往那里面加。

想临时试另一份表（不动安装目录里的）：

```
set DAPFLASHER_MCU_DB=I:\la_cache\mcu-ids-test.txt
```

对应代码：`src/target/mcudb.cpp`（解析 + 探测），内置副本是文件里的 `kDefaultTable`。

## 能识别到什么粒度

**只能到子系列，不能到料号。** `0x450` 同时对应 STM32H743VIT6、STM32H743ZIT6、
STM32H750VBT6 —— 封装、引脚数、容量这些信息不在 `DBGMCU_IDCODE` 里：

- 容量要看各系列的 FLASH 容量寄存器（STM32F1 是 `0x1FFFF7E0`，F2/F4 是 `0x1FFF7A22`，
  H7 没有这个寄存器，`0x1FF1E880` 处是 96 位 UID），不同系列地址不一样，收益有限；
- 引脚/封装完全没有寄存器暴露，只能从丝印或工程文件知道。

所以界面显示 `STM32H743/753 (Cortex-M7)` 这种「子系列（内核）」的形式。

## 为什么不从下载算法里提取

`.FLM` 的 `FlashDevice.DeviceName` 是**算法**的名字，不是芯片名字，例如：

```
STM32H7x_2048.FLM  -> DeviceName = "STM32H7x_2048"   （H7 系列，2 MB）
STM32F4xx_512.FLM  -> DeviceName = "STM32F4xx_512"
```

它有两个问题：

1. 粒度比 DEV_ID 更粗（`H7x` 覆盖 H742/H743/H750/H753 全部）；
2. 用户还没选算法时就没有算法名可显示，而识别目标恰恰发生在选算法之前。

反过来是有用的：识别出的子系列可以和算法名互相印证 —— 显示 `STM32H743/753`
而算法是 `STM32H7x_1024`，说明选错了容量档。

## 调试口 ID（DP IDCODE）

识别顺序上先应答的是**调试口本身**，不是芯片。SW-DP 的 IDCODE 是 ADIv5 的 DPIDR：

| 位 | 含义 |
|---|---|
| `[0]` | 恒 1（用来判断寄存器是否应答） |
| `[11:1]` | designer，JEP106 编码，`0x23B` = ARM Ltd |
| `[19:12]` | part number，SW-DP 回 `0x01`（ADIv5.1）或 `0x02`（ADIv5.2，支持 multidrop） |
| 其余 | 各厂商自己的版次编码，格式不统一，**不做猜测** |

实测这块 H743：`0x6BA02477` → `SW-DP v2, ARM, part 0x02`；
Cortex-M3/M4 的老目标回 `0x2BA01477` → `SW-DP v1, ARM, part 0x01`。

**它不能用来识别型号** —— 同一厂商同一代内核的 DP IDCODE 完全一样（F4 和 H7 都是 ARM
designer、part 0x01/0x02）。它的用处是回答「链路这一头到底是什么东西在应答」：
designer 不是 `0x23B`、part 不是 0x01/0x02 时，说明对面不是普通 SW-DP（JTAG-DP、
或者根本没连对），比继续往下读内存更有诊断价值。

代码：`describeDpIdCode()`（`src/target/mcudb.cpp`）。CLI 的 `--identify` 直接跟在
DP IDCODE 后面，窗口里在「目标」行的悬停提示里（`Debug port: …`）。

## 其他厂商

### Nordic nRF52

寄存器是 FICR 的 `INFO.PART`（FICR 基址 `0x10000000`，偏移 `0x100`），20 位料号：

| 值 | 器件 |
|---|---|
| `0x52840` | nRF52840 |
| `0x52833` | nRF52833 |
| `0x52832` | nRF52832 |
| `0x52820` | nRF52820 |
| `0x52811` | nRF52811 |
| `0x52810` | nRF52810 |

同一片 FICR 里 `INFO.FLASH`（`0x110`）、`INFO.RAM`（`0x10C`）、`INFO.PACKAGE`（`0x108`）
分别是 KB 数和封装代号，想显示容量可以再加一次读。

### Artery AT32

`DEBUG_IDCODE` 在 `0xE0042000`，32 位，高 16 位是系列、低位带容量与封装：

| 值（掩码 `0xFFFF0000`） | 器件 |
|---|---|
| `0x70050000` | AT32F403A/407（`0x70050242` 即 AT32F403ARCT7） |

更细的料号需要把 `0xE0042000` 的 32 位与 `0x1FFFF7F3` 处的 project id 拼成 64 位
再查表（Artery 官方 AN 的 `AT32_MCU_ID_TABLE` 就是这么做的），比这里做的粒度细得多；
本工具只需要「够用来选算法」的粒度，所以停在系列一级。

### 故意没收录的

- **GD32**：`DBG_ID` 与它替代的 STM32 同地址、同值 —— GD32F303 和 STM32F405 都回
  `0x413`，GD32F103 和 STM32F103 都回 `0x414`。认成哪个都是抛硬币，宁可显示成系列名。
- **NXP LPC / Kinetis**：`SIM_SDID` 地址逐系列不同，且 LPC 多数型号没有等价寄存器。
- **WCH CH32V**：RISC-V，没有 ARM 的 `DBGMCU`；其 `ESIG` 区在 `0x1FFFF7E0` 附近，
  格式逐系列不同，且本工具目前只烧 Cortex-M。
- **Raspberry Pi RP2040**：`SYSINFO_CHIP_ID` 固定读回 0，落不进「非 0 非全 1」的判据。

## 加一个新厂商

只改 `mcu-ids.txt`，不用重新编译：

1. 在参考手册里找到该厂商的「器件 ID」寄存器地址和值宽度；
2. 按 `地址 | 值 | 厂商 | 器件名 | 掩码` 加行，地址相同的行共用一次探测。

位宽不是 12 位也没关系 —— 掩码列就是为这个存在的。只有一种情况要改代码：
寄存器里的 ID 需要移位或者跨两个寄存器拼（例如 Artery 的 64 位料号，
或某些厂商把 ID 放在高字节）。

## 验证记录

WeAct-MiniSTM32H7xx（STM32H743VIT6）实测，有 `mcu-ids.txt` 和删掉它两种情况输出一致：

```
Target: Cortex-M7
CPUID: 0x411fc271
DP IDCODE: 0x6ba02477 (SW-DP v2, ARM, part 0x02)
MCU: STM32H742/743/750/753 (STMicroelectronics, device id 0x00000450, rev 0x00002003)
State: running
```

窗口里的「目标」一行显示 `STM32H742/743/750/753 (Cortex-M7)`；
悬停提示里是 `CPUID … , DP IDCODE … , core …`，再加 `Debug port: …` 和
`Vendor device id …` 两行。
